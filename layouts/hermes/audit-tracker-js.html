The light one

289 lines of JavaScript against PayGuard's 1,627 — and you were right that it is light. No jobs, no entries, no types: a month is a bucket, and you push numbers into it.

That subtraction is why the file is worth reading. It is not a smaller version of the other one; it answers a different question, and it contains the single most product-aligned function in either file.

The good part Keep

Hours from a rate — liveupdatePlan()

Eight lines, no dependencies, recalculating on every keystroke.

const monthlyHours = effectiveLimit / rate; const weeklyHours = monthlyHours / 4.33;

This is the product's headline rule, implemented. Nothing is hard-coded — the answer is 10 hours at $21.50, 15 at $15, 6 at $35, exactly as the brief demands, because it is derived every time rather than written down once.

It also lets the reader edit the limit itself, so someone whose figure differs from the built-in $1,210 is not stuck with a wrong answer.

KeepSee the Wrong list — it answers "hours from zero", not "hours left". The equation is right; the input is not.
The month cells count down, not uprenderMonths()

Every cell shows what is left, not what was earned — an untouched month reads $1,210, not $0, and a month that went over stops showing money entirely and says ⚠ Over.

It is one line of display logic and it changes what the grid is for. A row of zeros is a record; a row of ceilings is a plan. The decision the reader is making is how much room they have, and this is the only surface in either file that answers it without arithmetic.

KeepThe strongest idea in this file after updatePlan, and it costs nothing.
Consequence before commitopenLogModal()

Opening the log dialog computes what will be left after the entry and colours it green, amber or red before anything is saved. Teaching by interaction, as the brief asks.

KeepPayGuard's modal has no equivalent. Cross it in.
One threshold, applied everywhererenderHeroStats · renderMonths · openLogModal

0–80% clear, 80–100% close, over 100% over. The same three bands drive the ring colour, the ring's sentence, the remaining figure, every month cell and the modal preview. Change one number and the whole page agrees with itself.

KeepThe threshold is repeated as a literal in four places rather than named once. Same behaviour, one constant away from being maintainable.

Wrong Fix before reuse

The year never advancesloadState()
if (!parsed.year) parsed.year = new Date().getFullYear();

The year is stamped once, on first run, and never updated again. Nothing in the interface changes it. Come January the app keeps showing last year's months, last year's total and last year's limit, with this year's data being filed under a key the display no longer reads.

Every downstream figure inherits it — monthKey, yearTotal, overMonthsCount and the "2026 Total" heading.

FixThe most damaging bug in the file, and invisible for eleven months of testing.
"Hours I could work" ignores what you already earnedupdatePlan()

The card is headed "How many hours could I work this month?". The function divides the full monthly limit by the rate and never subtracts what has already been counted.

So on the 28th of a month where you have earned $1,100 of your $1,210, it still answers 56 hours. The correct answer is five. It is wrong in the direction that costs someone their benefits, which is the one direction the brief singles out.

FixUse remaining, not the limit. One term. This is the difference between a calculator and an answer.
Entries from other years leak into the listrenderLogs()
const [year, month] = key.split('-'); // `year` is destructured and never used all.push({ monthIndex: parseInt(month) - 1, amount, idx }); ... <span class="log-date">${name} ${state.year}</span> // stamped with the CURRENT year

The loop walks every key in storage regardless of year, then labels each row with state.year. A 2026 entry and a 2027 entry for the same month appear as two identical rows, both claiming the same date.

FixThe variable that would have prevented it is already destructured on the line above.
Logs are push-onlyconfirmLog() · clearAllLogs()

state.logs[key].push(amount) is the only write. There is no edit, no delete, no undo — the only correction available is "Clear all", which wipes every month of every year.

The bare number array is why: an entry has no id, no date and no note, so there is nothing to address it by. That is the same subtraction that makes the file small, and this is its bill.

FixA mistyped amount currently costs the reader their whole history. Entries need identity.
Rejection is silentconfirmLog()

if (!amount || amount < 0) { focus(); return; } — a blank or zero entry just moves the cursor. Nothing is said. The reader presses "Log It" and the dialog sits there.

FixIt also rejects 0, which is a legitimate thing to record for a month with no work.
Safe only because nothing is typedrenderMonths · renderLogs

Rows are built with innerHTML templates and buttons with setAttribute('onclick', …). There is no free-text field anywhere in the app, so nothing hostile can reach either. Add a notes field and both become injection points on the same day.

DecideNot a bug today. It is a trap laid for whoever adds the feature PayGuard already has.

On interface and framing: yes, four things. These are not calculations, which is exactly why they survived the comparison — they are decisions about what to put on screen.

Cells count downShowing the ceiling instead of the total. Turns a record into a plan. Nothing in the eight layouts does this.
Nav that scrollsOne page, always rendered, scrollIntoView instead of a router. Removes mount/unmount and lost scroll position from a whole class of layout.
Consequence previewWhat will be left, shown before you commit, updating as you type.
Status as three pillsAlways visible, one tap, no select. Beats a dropdown everywhere it appears.

And one gap neither side has closed. hours → rate — "I can manage 10 hours, what can I be paid?" — is absent from all eight layouts, from src/domain/, and from both hermes files. The brief calls it the actual job-search criterion. It is the same equation solved for the other unknown, and nobody has written it.

The shape of the answer: mine these files for interface, and wire that interface to src/domain/. Every prototype calculation is either behind what exists or duplicating it, and two of them — PayGuard's gauge and its trial-month tracker — are confidently wrong about someone's benefits.
